# Facet Scoring Baseline

A compact, production-minded baseline that evaluates conversation text against a large, heterogeneous facet catalogue — without ever sending the whole catalogue to an LLM in one prompt, and without letting the LLM invent scores for things conversation text cannot actually support (medical values, clinical diagnoses, psychometric test results).

## Setup

Requirements: Python 3.10+, [Ollama](https://ollama.com) installed and on PATH, ~5GB free disk for the model.

```bash
pip install -r requirements.txt
ollama serve &                       # start the local inference server
ollama pull qwen2.5:7b-instruct      # ~4.7GB, Apache-2.0 licensed, 7B params
```

## Run order

```bash
python src/preprocess.py     # Part 1: audit + enrich the raw facet CSV
python src/embed_index.py    # builds the local embedding index (regenerable, gitignored)
python eval/run_eval.py      # Part 3: runs the benchmark, writes eval/report.md
python hallucination_demo/naive_baseline.py   # naive-vs-gated contrast, prints to stdout
```

Everything downstream of `data/raw/Facets Assignment.csv` is generated by these scripts — nothing in `data/processed/` is hand-edited.

```bash
pytest tests/ -v              # 17 unit tests, no LLM/network required
```

## Architecture

```
raw CSV (399 rows, single "Facets" column)
  │
  ▼  src/preprocess.py + src/taxonomy.py   (deterministic, reproducible)
  │     - normalize (strip scrape-artifact ID prefixes, camelCase split, trailing colons)
  │     - detect header-artifact rows (30 found: "Democratic Leadership:", etc.)
  │     - classify facet_type via regex/keyword rules (8 categories)
  │     - derive conversation_observable / sensitivity / abstention_reason
  │     - build templated 5-level ordinal scoring anchors
  ▼
data/processed/facets_enriched.csv + AUDIT_SUMMARY.md
  │
  ▼  src/embed_index.py  (sentence-transformers, all-MiniLM-L6-v2, local, no API)
  │     embeds all non-header facets (369 of 399)
  ▼
data/processed/facet_index.npz
  │
  ▼  conversation text comes in  ───────────────────────────────┐
  │                                                              │
  ▼  src/retrieve.py: FacetRetriever.retrieve()                 │
  │     top-k by cosine similarity over the FULL index           │
  │     (includes non-observable facets on purpose -- see below) │
  ▼                                                              │
  taxonomy gate (retriever.split_by_taxonomy_gate)               │
  ├── conversation_observable == False  ─────────────────────────┤
  │     -> status="not_observable", source="taxonomy_gate"       │
  │     (LLM is NEVER called for these)                          │
  │                                                               │
  └── conversation_observable == True                            │
        -> src/score.py: batched (default 8/batch) LLM calls     │
           -> src/llm_client.py: Ollama chat endpoint, JSON mode  │
           -> independently re-validated in Python: invalid       │
              status/score/confidence downgraded to               │
              insufficient_evidence; omitted/unknown facet_ids    │
              reconciled so every requested facet gets a row      │
  │
  ▼
src/pipeline.py: evaluate_conversation() merges both paths into one uniform result list
```

### Why retrieval sees non-observable facets but the LLM never does

This is the core anti-hallucination mechanism (`DECISIONS.md` #2). The embedding index deliberately includes medical/clinical/cognitive facets so retrieval can demonstrate they'd genuinely surface as topically relevant (e.g. `FSH level` for a fertility-related conversation) — and then the **taxonomy gate**, a deterministic Python check with no LLM in the loop, blocks them before any prompt is ever constructed. See `hallucination_demo/` for three concrete cases and a side-by-side naive-baseline contrast.

## Facet audit findings (Part 1)

Full detail in `data/processed/AUDIT_SUMMARY.md`. Highlights:

| facet_type | count |
|---|---|
| personality_trait_or_disposition | 258 |
| spiritual_religious_practice | 34 |
| header_artifact (not real facets) | 30 |
| behavioral_frequency_count | 25 |
| cognitive_psychometric | 23 |
| medical_biological | 13 |
| clinical_psychological_scale | 9 |
| sensitive_biographical | 7 |

- **30 rows (7.5%) are section-header scraping artifacts**, not facets at all (`"HEXACO Personality Inventory Facets:"`, `"Numerical Reasoning Subcomponents:"`) — detected by trailing-colon heuristic, excluded from the embedding index entirely.
- **31 rows carry a leading `NNN. ` numeric-ID scrape artifact** (mostly numbered spiritual-practice entries like `"800. Sufi practice: Sufi retreat attendance count"`) — stripped during normalization, ID preserved in a separate column.
- **45 rows (13, medical + 9, clinical + 23, cognitive = 45) are gated non-observable** — they require lab tests, clinical diagnosis, or formal psychometric testing and can never be conversationally scored, regardless of what's said.
- **0 exact duplicate normalized values** were found in this catalogue (checked, not assumed).
- 3 rows had a `SelfEsteem`/`Selfcontrol`-style missing-space concatenation artifact, fixed by camelCase-boundary splitting.

## Benchmark findings (Part 3)

Live run against `qwen2.5:7b-instruct`, full detail in `eval/report.md`: **18/20 reference rows matched (90%)**, across 12 conversations (clear/ambiguous/contradictory/quoted/sarcastic/code-switched/low-evidence) and 22 facets spanning all 8 taxonomy types.

**The 3 required hallucination-bait cases (`FSH level`, `Sleep Apnea`, `Intelligence Quotient (IQ)`) all correctly abstained via the taxonomy gate** — see `hallucination_demo/examples.md` for the live naive-vs-gated contrast (the naive baseline confidently scored all three; e.g. it scored `FSH level` a 2/5 while its own stated reason admits "does not specify FSH level").

Two genuine failures surfaced, both informative rather than embarrassing to report:
- **Misattribution (quoted speech, `C04`):** the speaker quotes their sister saying "I never think before I act, I just leap" while describing *themself* as a heavy planner. The system scored the speaker's `Risktaking` at 5/5, and its own logged reason literally says *"the sister's statement clearly indicates..."* — it scored the wrong person's trait. This is a `WRONG_SCORE` outcome, not a taxonomy-gate failure (Risktaking is legitimately conversation-observable); it's a reasoning failure on speaker attribution.
- **Contradiction resolved by recency, not abstention (`C03`):** given "I trust people completely... actually no, I don't trust a single person," the model scored `Trust in others` at 1/5 with 0.95 confidence, reasoning only from the second half of a directly self-contradictory statement. This is the one `HALLUCINATION`-classified row in the benchmark (expected abstain, got a confident score) — see `DEBUGGING.md` #6 for the diagnosis, the system-prompt fix, and its narrow verification.

Both are documented rather than hidden or silently patched away, per the brief's emphasis on honest failure analysis over polish.

## Known limitations

- Taxonomy classification is keyword/regex-based (see `DECISIONS.md` #1) — some genuinely ambiguous facets (e.g. `Psychoticism`, `Attachment style: Secure`) get a coarser label than a human or an LLM classifier might assign.
- Scoring anchors are a generic template substituting the facet name in (see `DECISIONS.md` #4), not hand-authored per facet — weaker for facets where "high"/"low" aren't self-evident from the name alone.
- Qwen2.5-7B on a 4GB-VRAM laptop GPU runs with partial CPU offload, so single-batch latency is several seconds to tens of seconds depending on load — fine for this benchmark's scale, not production-throughput.
- The reference-label set (Part 3) is intentionally partial (~20 rows across 12 conversations), not an exhaustive facet x conversation matrix, per the brief.

## What I'd improve with another day

1. **Hand-author richer scoring anchors for the highest-retrieval-frequency facets**, keeping the generic template as fallback for the long tail — prioritized by actual usage rather than guessed upfront (ties into the 5000-facet scale discussion below).
2. **Add an LLM-assisted second pass over taxonomy-ambiguous rows** (flagged by the rule-based classifier with a confidence score) rather than an all-or-nothing rule-based vs LLM-based choice.
3. **Cache embeddings + LLM verdicts keyed on (facet_id, conversation_hash)** so repeated evaluation of the same conversation (e.g. during iterative benchmark development) doesn't re-call the LLM.
4. **Calibration check**: compare the model's stated `confidence` against actual agreement rate in the benchmark (a simple reliability diagram) — flagged as brownie-points territory, not attempted here given the 24h window.
5. Swap the flat numpy cosine-similarity retrieval for FAISS/HNSW once facet count materially exceeds what fits comfortably in memory (see below).

## Scale note: how this design handles 5,000 facets

- **Indexing/retrieval:** The embedding step (`src/embed_index.py`) is already fully vectorized and facet-count-agnostic — encoding 5,000 short strings with `all-MiniLM-L6-v2` is a few seconds of one-time work. The current *search* is a brute-force `embeddings @ query_embedding` matrix-vector product (369x384 floats today) — at 5,000 facets that's still under 10MB and sub-millisecond per query, so a flat index would likely still be fine. The documented upgrade path is FAISS (`IndexFlatIP` for exactness, or `IndexHNSWFlat` for approximate sub-linear search past ~50k-100k items) — a swap-in replacement for the `retrieve()` method's similarity search, not an architecture change.
- **Batching:** Batch size stays fixed (default 8 facets/call) regardless of catalogue size — it's bounded by prompt-length/attention budget and by keeping each LLM call's JSON output small enough to parse reliably, not by facet count. More facets means more batches per conversation only insofar as `top_k` (how many candidates retrieval returns) is raised; `top_k` itself should scale sub-linearly with catalogue size (the point of retrieval is precisely that you don't need more candidates just because the catalogue grew).
- **Model calls:** Per-conversation LLM calls = `ceil(top_k / batch_size)`, independent of total catalogue size. This is the entire point of the retrieve-then-score design over a "score everything" design, whose cost would scale linearly with catalogue size.
- **Caching:** The natural cache key is `(facet_id, conversation_hash)` — once a conversation has been scored against a facet, that verdict never needs recomputing unless the conversation or the facet's anchors change. At 5,000 facets with a modest `top_k` (say 20-30), most conversations still only touch a small slice of the catalogue, so cache hit rate should climb quickly across a realistic conversation stream (repeated topics, similar phrasing).
- **Latency:** Dominated by LLM call count x per-call latency, not by embedding search (negligible at this scale) or the taxonomy gate (a dict/set lookup). First bottleneck to watch: **local single-GPU throughput**, since batches for one conversation are currently called sequentially. Parallelizing independent batch calls (they don't depend on each other) or moving to a hosted inference endpoint with real concurrency would be the first thing to change before facet count itself becomes the bottleneck.
- **Where I'd expect the first real bottleneck at 5,000 facets:** not retrieval (embeddings scale fine), not the taxonomy gate (O(1) per candidate) — it's **sequential LLM call latency** if `top_k` needs to grow to maintain recall across a much larger and more topically diverse catalogue. The fix is concurrency (async/parallel batch calls) and/or a second, cheaper filtering stage (e.g. a lighter-weight or non-LLM relevance re-ranker) between "retrieve top 200 by embedding" and "LLM-score top 20-30" — an extra funnel stage, not a redesign of the existing one.
