01 — System design

How a conversation becomes a set of scores

Retrieval sees the entire facet index — including facets that can never be safely scored — so the taxonomy gate has something real to block, not a pre-filtered list.

The taxonomy gate is deterministic, not a prompt instruction. Medical, clinical, and cognitive-testing facets are blocked in Python — a plain bool check — before a prompt is ever built for them. A stochastic model being told "please don't hallucinate" is never the only safeguard here.

03 — Part 2

Retrieval, the taxonomy gate, and robust scoring

Real code from the repo — not paraphrased. Retrieval does a flat cosine-similarity search over the full index; the gate is one boolean check standing between retrieval and any LLM call.

src/retrieve.py
def retrieve(self, conversation_text: str, top_k: int = 20) -> list[dict]:
    query_emb = self.model.encode([conversation_text], normalize_embeddings=True)[0]
    sims = self.embeddings @ query_emb  # cosine sim, both L2-normalized
    top_idx = np.argsort(-sims)[:top_k]
    return [self._facet_row_to_candidate(self.facet_ids[i], sims[i]) for i in top_idx]

@staticmethod
def split_by_taxonomy_gate(candidates):
    llm_eligible     = [c for c in candidates if c["conversation_observable"]]
    taxonomy_blocked = [c for c in candidates if not c["conversation_observable"]]
    return llm_eligible, taxonomy_blocked

Scoring re-validates the model's output independently — an invalid score or status is never trusted as-is, and the reason for the downgrade survives instead of being silently discarded:

src/score.py
if status == "scored":
    try:
        score = int(score)
        if not (1 <= score <= 5):
            raise ValueError
    except (TypeError, ValueError):
        status = "insufficient_evidence"   # never trust an out-of-range score
        note = f"invalid_score_value:{item.get('score')!r}"
        score = None

def test_missing_facet_in_llm_response_still_produces_a_row():

06 — Found, fixed, re-verified

One hallucination, on the record

The first full benchmark run wasn't 0/20 — it was 1/20. The fix attempt that failed stayed in the log next to the one that worked.

Found — live benchmark run

C03: "I trust people completely… actually no, I don't trust a single person"

Scored confidently — 1/5, 0.95 confidence — by resolving a direct self-contradiction via recency instead of abstaining.

Attempt 1 — verified not to work

Abstract system-prompt rule

"Don't resolve contradictions by trusting whichever statement came last." Checked narrowly on this exact case before committing to a full re-run.

result: identical output — the rule alone didn't change the model's behavior
Attempt 2 — verified working

Concrete worked example in the prompt

Same case, spelled out as a wrong answer vs. a right answer. Re-checked the same single call.

result: correct insufficient_evidence, citing the contradiction itself
Shipped — full re-verification

Re-ran all 12 conversations, not just the one facet

A prompt change affects every future call — it doesn't get trusted until it's checked against everything it could have broken, not just the case it was written for.

final: 90% agreement, 0/20 hallucinations, no regressions

07 — Process

Engineering decisions and debugging

6 non-trivial decisions, 7 real bugs — full detail in DECISIONS.md and DEBUGGING.md.

Decisions
01
Deterministic taxonomy rules over LLM classification
Reproducibility of the audit stage mattered more than marginal nuance on borderline facets.
02
Anti-hallucination guarantee lives in Python, not a prompt
A stochastic model can't be the only thing standing between it and a hallucination.
03
Qwen2.5-7B via Ollama
The largest model that actually runs end-to-end within the 4GB-VRAM budget, not the largest on paper.
04
Generic anchor template, not 399 hand-written rubrics
Reproducible coverage now; hand-authoring prioritized later by real retrieval frequency.
05
Embedding ablation, extended twice
Bare name beat name+type; a stronger model (BGE) improved mean rank but not Recall@8/20 — mixed result, reported as such.
06
Disclosed retrieval recall as its own number
A code-comment caveat isn't the same as an actually-surfaced one — see the benchmark section above.

08 — Optional: comparison/ablation

Three retrieval configurations, tested honestly

Extended twice after a self-critique pass flagged retrieval recall as the weakest part of this system. Neither extension produced a clean win — both are reported as found.

Read this next to the benchmark's 90% agreement number: that figure validates the scoring stage only. This system's eval/run_eval.py force-includes reference facets so the scorer always sees them — organic, unassisted retrieval alone finds only 9/20 (45%) of them at the benchmark's top_k=8. The taxonomy gate's 0/20 hallucination guarantee is untouched by this (it depends on facet_type, not retrieval), but retrieval recall is the real, disclosed weak point of the current system.

Genuinely mixed, not smoothed over: BGE has by far the best mean rank — it rarely buries a facet catastrophically (e.g. Intelligence Quotient (IQ) ranks 139th under BGE vs. 330th under MiniLM) — but it does not beat the ablated MiniLM config on Recall@8 or Recall@20, the cutoffs this system actually uses. 09 — Looking ahead

Scaling to 5,000 facets

You don't need to run all 5,000 to reason about where this design bends.

indexing
Still ~seconds
Fully vectorized, facet-count-agnostic
→
retrieval
FAISS/HNSW swap-in
Flat search fine to ~50-100k; then a drop-in replacement, not a redesign
→
model calls
ceil(top_k / batch)
Independent of total catalogue size
→
bottleneck
Sequential call latency
Fix: parallel batches + a cheaper re-ranking funnel stage
  • Caching: natural key is (facet_id, conversation_hash) — most conversations only ever touch a small slice of a 5,000-facet catalogue.
  • First real bottleneck: not retrieval, not the taxonomy gate (both stay fast) — it's sequential LLM call latency if top_k has to grow to hold recall over a larger, more diverse catalogue.
